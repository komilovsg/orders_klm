# Техническое задание

## Полноценная веб-панель управления закупками и планом оплат КЛМ

**Назначение документа:** готовое задание для Codex на разработку полноценного рабочего веб-приложения на основе существующей автономной HTML-панели.

**Базовый файл-прототип:** `ПЛАН_ОПЛАТ_с_фильтрами.html`.

**Ключевое правило:** существующая панель является утверждённым функциональным и визуальным прототипом. Нельзя удалять, упрощать или самовольно переименовывать готовые разделы, справочники, поля, расчёты, фильтры, импорт документов и бизнес-правила. Новая система должна перенести их в полноценную клиент-серверную архитектуру.

---

# 1. Инструкция для Codex

Разработай полноценное локальное веб-приложение для управления закупками, заказами, потребностями проектов, тендерами, счетами поставщиков и планом оплат.

Перед началом разработки:

1. Изучи существующий HTML-файл панели полностью.
2. Составь карту существующих функций и сопоставь их с данным ТЗ.
3. Не заменяй рабочие функции заглушками.
4. Не удаляй данные, справочники и существующие восемь разделов плана оплат.
5. Не меняй визуальный стиль без отдельного согласования.
6. Выполняй разработку по этапам, указанным в разделе «Порядок реализации».
7. После каждого этапа запускай автоматические тесты и показывай рабочий результат.
8. Любое спорное или неоднозначное сопоставление данных отправляй на ручную проверку, а не подтверждай автоматически.
9. Все изменения данных должны сохраняться в базе данных и фиксироваться в журнале действий.
10. Нельзя хранить рабочие данные только в `localStorage` или `IndexedDB` браузера.

## 1.1. Что считать готовым результатом

Готовый результат — приложение, которое:

- запускается на локальном сервере Windows;
- открывается в Chrome или Edge по адресу `http://localhost:3000`;
- хранит справочники, заказы, счета, связи, тендеры и план оплат в PostgreSQL;
- хранит исходные файлы счетов и импортов в выделенной папке или локальном объектном хранилище;
- обрабатывает новые документы в фоне;
- не теряет данные после закрытия браузера или перезагрузки компьютера;
- поддерживает резервное копирование и восстановление;
- имеет четыре основные вкладки: `ОБЩЕЕ`, `ЗАКАЗ`, `ПЛАН ОПЛАТ`, `ТЕНДЕР`;
- сохраняет текущую цветовую схему, размеры карточек, стиль кнопок, таблиц и фильтров;
- проходит все критерии приёмки из этого ТЗ.

# 2. Цель системы

Система должна восстановить и автоматизировать полный процесс закупки:

1. ведение справочников;
2. загрузка потребности по проектам;
3. формирование нового заказа;
4. подбор ТМЦ для запроса поставщикам;
5. создание тендера;
6. получение и распознавание счетов;
7. построчное сравнение предложений;
8. выбор поставщика или распределение объёма между несколькими поставщиками;
9. подтверждение заказа;
10. формирование плана оплат;
11. учёт оплат и сальдо;
12. исключение полностью оплаченных счетов;
13. контроль необработанной потребности;
14. проверка поставщиков и хранение истории оценки.

# 4. Рекомендуемая архитектура

## 4.1. Технологический стек

Использовать следующий стек, если в существующем репозитории нет другой утверждённой архитектуры:

- frontend: `Next.js + React + TypeScript`;
- UI: CSS Modules или Tailwind с точным воспроизведением существующего стиля;
- backend API: `FastAPI + Python`;
- ORM и миграции: `SQLAlchemy + Alembic`;
- база данных: `PostgreSQL`;
- фоновые задачи: `Celery + Redis` либо `RQ + Redis`;
- планировщик: `Celery Beat` или `APScheduler` на сервере;
- локальное файловое хранилище: `MinIO` или каталог, подключённый как Docker volume;
- чтение Excel: `openpyxl`, `pandas`;
- чтение PDF: `PyMuPDF`, `pdfplumber`;
- OCR: локальный `Tesseract OCR` с языками `rus+eng`;
- тесты backend: `pytest`;
- тесты frontend: `Vitest + React Testing Library`;
- end-to-end тесты: `Playwright`;
- запуск: `Docker Compose`.

## 4.2. Приоритет размещения

Основной вариант — локальный сервер на компьютере или сервере компании.

Пример структуры на Windows:

```text
C:\KLM\procurement-panel\          исходный код и docker-compose
C:\KLM\procurement-data\           рабочие данные
C:\KLM\procurement-data\files\     сохранённые документы
C:\KLM\procurement-data\imports\   папки автоматического импорта
C:\KLM\procurement-data\backups\   резервные копии
```

Папки автоматического импорта:

```text
imports\requirements\   потребность
imports\invoices\       счета
imports\payments\       оплаты
imports\balances\       сальдо
imports\supplier-risk\  выгрузка ИНН и ЗСК
```

Пути должны настраиваться администратором через интерфейс и переменные окружения. Нельзя жёстко привязывать программу к имени пользователя Windows.

## 4.3. Часовой пояс

Ввести настройку `APP_TIMEZONE`.

Значение по умолчанию: `Europe/Moscow`.

Все фоновые задачи, даты формирования отчётов и история изменений должны использовать заданный часовой пояс.

# 6. Лист «ОБЩЕЕ»

На листе отображаются четыре основных окна, расположенные вертикально слева:

1. `Перечень одобренных ПОСТАВЩИКОВ`;
2. `Перечень ПЛАТЕЛЬЩИКОВ`;
3. `Используемые ТМЦ`;
4. `ЦЕНЫ закупки (ценообразование)`.

Каждое окно раскрывается вниз. Другие окна не смещаются горизонтально и не накладываются на содержимое. Одновременно показывается содержимое только активного окна верхнего уровня.

## 6.1. Одобренные поставщики

Сохранить существующие 65 поставщиков как начальные данные.

При раскрытии список отображается в четырёх столбцах и в алфавитном порядке.

Для каждого поставщика хранить и показывать:

- краткое наименование;
- полное юридическое наименование;
- ИНН;
- КПП, если применимо;
- ОГРН / ОГРНИП;
- статус: активен, неактивен, исключён;
- дата добавления;
- категория поставляемых ТМЦ;
- контактные данные;
- комментарий;
- уровень риска ЗСК;
- источник оценки;
- дата и время последней проверки;
- история изменения оценки.

### 6.1.1. Светофор ЗСК

Отображать рядом с поставщиком общепринятый индикатор:

- зелёный — низкий уровень риска;
- жёлтый — средний уровень риска;
- красный — высокий уровень риска;
- серый — данные отсутствуют или проверка не выполнена.

Корректное название показателя в интерфейсе: `Уровень риска ЗСК`.

Не называть его полной экономической надёжностью, платёжеспособностью или финансовой устойчивостью: ЗСК отражает уровень риска вовлечённости в подозрительные операции.

### 6.1.2. Обновление ИНН и ЗСК

Создать адаптер внешнего источника `SupplierRiskProvider`.

Поддержать два режима:

1. официальный API сервиса при наличии договора, URL и токена;
2. импорт последнего файла Excel/CSV из папки `imports\supplier-risk`.

Требования:

- задача запускается ежедневно в 09:00 по `APP_TIMEZONE`;
- токены хранятся только на сервере в секретах, а не во frontend-коде;
- при недоступности источника предыдущие данные не стираются;
- поставщик получает статус `Проверка не выполнена`, а ошибка пишется в журнал;
- ИНН нельзя определять только по похожему названию, если найдено несколько организаций;
- неоднозначные совпадения попадают в очередь ручной проверки;
- для каждой проверки сохраняются источник, время и исходный ответ;
- должен быть ручной запуск `ОБНОВИТЬ ДАННЫЕ`;
- должен быть отчёт о результате: проверено, обновлено, не найдено, требует проверки, ошибки.

Не реализовывать несанкционированный сбор данных из Telegram-бота или обход ограничений сайта. Если сервис не предоставляет API, использовать только согласованную выгрузку.

# 7. Лист «ЗАКАЗ»

# 7.1. Раздел 01 «Реквизиты заказа»

Поля располагаются в одну строку, как в текущей панели:

1. `Наименование ПОСТАВЩИКА` — фильтр `ПОДБОР`;
2. `Наименование ПЛАТЕЛЬЩИКА` — фильтр `ПОДБОР`;
3. `№ счёта Поставщика` — заполняется только после прикрепления реального счёта поставщика;
4. `Наименование ПРОЕКТА` — фильтр `ПОДБОР` с возможностью выбрать несколько проектов;
5. блок загрузки `ПОТРЕБНОСТЬ`.

Нельзя автоматически заполнять номер счёта на основании номера заказа, проекта или другого документа.

В фильтрах поставщика, плательщика и проекта после выбора должно отображаться выбранное значение. Нельзя оставлять `ПОДБОР 1` или просто `ПОДБОР`, если выбор применён.

## 7.2. Импорт потребности

Источником является реестр потребности Excel/CSV.

Система должна:

- наблюдать за папкой `imports\requirements`;
- поддерживать ручную загрузку файла;
- распознавать заголовки по названию, а не только по фиксированному номеру колонки;
- использовать колонку `Название проекта` как источник проектов;
- поддерживать прежний источник, где проект находился в столбце O;
- не повторять одно название проекта более одного раза в фильтре;
- загружать полный список ТМЦ выбранного проекта;
- показывать имя и дату исходного файла;
- записывать протокол импорта;
- обновлять данные без создания дублей;
- сохранять предыдущую успешную версию при ошибке нового файла.

Для совместимости с существующим реестром учитывать:

- наименование ТМЦ;
- единицу измерения;
- количество;
- номер заказа;
- название проекта;
- возможные количества в штуках/метрах и килограммах.

## 7.3. Раздел 02 «Потребность в ТМЦ»

Таблица:

1. №;
2. Наименование ТМЦ;
3. ТМЦ — checkbox выбора позиции;
4. Ед.;
5. Количество;
6. Цена без НДС;
7. НДС;
8. Итого;
9. действие удаления для вручную добавленной позиции.

Фильтр в столбце `ТМЦ`:

- все;
- отмеченные;
- неотмеченные.

Снабженец отмечает позиции, которые войдут в запрос поставщику или тендер.

Каждая позиция имеет одну основную единицу измерения. Альтернативные единицы и коэффициенты разрешаются только после их настройки в справочнике.

## 7.4. Раздел 02.1 «НЕ ЗАКАЗАНО»

Формируется автоматически для выбранного проекта.

Показывает позиции, которые:

- отсутствуют в выбранных предложениях поставщиков;
- закрыты выбранными предложениями частично;
- требуют ручного сопоставления.

Колонки:

1. выбор позиции;
2. наименование ТМЦ;
3. единица измерения;
4. требуется по проекту;
5. подтверждено выбранными счетами;
6. осталось заказать;
7. найденные счета;
8. статус;
9. действие.

Формула:

```text
Осталось заказать =
Количество по потребности − количество по выбранным предложениям
```

Статусы:

- `Не заказано`;
- `Заказано частично`;
- `Заказано полностью`;
- `Требует проверки`.

Действия:

- `Добавить в тендер`;
- `Привязать строку счёта`;
- `Открыть счёт`;
- `Подтвердить сопоставление`.

Если позиция закрывается несколькими счетами, показывать их в раскрывающейся детализации.

Индикатор:

```text
Необработанные позиции: N
```

Предупреждение:

```text
По проекту осталось N позиций без подтверждающего счёта.
```

Цвета:

- красный — счёт отсутствует;
- жёлтый — заказано частично;
- серый — требуется сопоставление;
- зелёный — заказано полностью.

Кнопка `Показать необработанные` прокручивает экран к этому блоку и включает фильтр необработанных позиций.

## 7.5. Раздел 03 «Срок производства»

- количество рабочих дней;
- планируемая дата готовности;
- календарь;
- расчёт даты с учётом производственного календаря;
- возможность ручной корректировки даты.

## 7.6. Раздел 04 «Условия расчёта»

Три независимых условия:

1. процент в запуск;
2. процент перед отгрузкой;
3. процент после отгрузки через указанное количество рабочих дней.

Можно включить одно, два или все условия.

Для каждого условия:

- checkbox включения;
- процент;
- рассчитанная сумма;
- дата оплаты через календарь;
- для оплаты после отгрузки — дата отгрузки и количество рабочих дней.

Суммы рассчитываются от полного итога заказа.

## 7.7. Раздел 05 «Условия поставки»

Варианты:

- самовывоз;
- доставка поставщиком.

Поля:

- расстояние;
- стоимость доставки;
- доставка включена в счёт;
- доставка отдельным счётом;
- ориентировочная сумма;
- комментарий.

# 8. Обработка счетов поставщиков

Не создавать отдельную параллельную систему загрузки. Все документы проходят через единый сервис импорта.

## 8.1. Поддерживаемые форматы

- PDF;
- JPG/JPEG;
- PNG;
- TIF/TIFF;
- XLSX/XLS;
- CSV.

## 8.2. Этапы обработки

1. обнаружение нового или изменённого файла;
2. вычисление SHA-256;
3. проверка дубля;
4. сохранение исходного файла;
5. извлечение текста;
6. OCR для сканов;
7. распознавание реквизитов;
8. распознавание всех табличных строк;
9. определение поставщика;
10. определение плательщика;
11. определение проекта;
12. определение раздела плана оплат;
13. сопоставление строк с потребностью и тендером;
14. сохранение результата и показ уведомления.

## 8.3. Распознаваемые реквизиты

- номер и дата счёта;
- поставщик;
- ИНН и КПП поставщика;
- плательщик / покупатель;
- ИНН и КПП покупателя;
- проект;
- сумма без НДС;
- НДС;
- итоговая сумма;
- срок поставки;
- условия оплаты;
- назначение платежа;
- исходный файл.

Назначение платежа нельзя использовать как наименование поставщика.

## 8.4. Построчное распознавание

Для каждой строки счёта получать:

- исходный текст;
- нормализованное наименование ТМЦ;
- количество;
- единицу измерения;
- цену за единицу;
- сумму;
- НДС, если указан;
- уверенность распознавания;
- номер страницы и координаты строки для проверки.

Одна строка счёта — отдельная запись базы данных.

## 8.5. Сопоставление с потребностью

Приоритет сопоставления:

1. ручная подтверждённая связь;
2. точное совпадение внутреннего кода / артикула;
3. точное нормализованное наименование и совместимая единица;
4. утверждённый словарь синонимов;
5. нечёткое совпадение только как подсказка.

Если единицы измерения различаются, отсутствует коэффициент пересчёта или найдено несколько равнозначных позиций, установить `Требует проверки`.

Нечёткое совпадение не должно самостоятельно закрывать потребность.

## 8.6. Защита от дублей

Основной ключ файла: SHA-256.

Дополнительный бизнес-ключ счёта:

```text
ИНН поставщика + номер счёта + дата счёта + итоговая сумма
```

Повторное появление того же счёта:

- не создаёт новую запись;
- обновляет техническую информацию импорта;
- не дублирует строки;
- не дублирует оплату;
- не сбрасывает ручные сопоставления;
- не возвращает полностью оплаченный счёт в план оплат.

## 8.7. Уведомление после обработки

```text
Счёт №___ привязан к проекту.

Распознано позиций: N.
Сопоставлено с потребностью: N.
Требует проверки: N.
Осталось необработанных позиций: N.
```

Отдельно показывать:

- позиции потребности без счёта;
- строки счетов без привязки к потребности.

# 9. Лист «ТЕНДЕР»

Тендер формируется для конкретного проекта и выбранных позиций потребности.

## 9.1. Создание тендерной группы

Пользователь выбирает позиции в блоке `НЕ ЗАКАЗАНО` и нажимает `Добавить в тендер`.

Для каждой позиции создаётся тендерная группа с указанием:

- проекта;
- ТМЦ;
- единицы;
- требуемого количества;
- создателя;
- даты создания;
- статуса.

## 9.2. Выбор поставщиков

Поставщики выбираются из справочника одобренных поставщиков фильтром с несколькими значениями.

До получения счёта строка поставщика имеет статус `Счёт не получен`.

## 9.3. Таблица предложений

Колонки:

1. ТМЦ;
2. требуется;
3. поставщик;
4. номер счёта;
5. количество по счёту;
6. цена за единицу;
7. общая сумма;
8. срок поставки;
9. условия оплаты;
10. файл счёта;
11. статус;
12. действие.

Статусы предложения:

- `Счёт не получен`;
- `Получен`;
- `Требует привязки`;
- `Выбран`;
- `Отклонён`.

## 9.4. Автоматическое попадание счетов

После импорта нового счёта система:

1. определяет поставщика;
2. определяет проект;
3. распознаёт все строки;
4. ищет соответствующие активные тендерные позиции;
5. добавляет предложения поставщика;
6. прикрепляет исходный файл;
7. устанавливает статус `Получен`.

Система обязана проверить также ранее загруженные счета без повторной загрузки.

## 9.5. Блок «ТРЕБУЕТ ПРИВЯЗКИ»

Если проект или ТМЦ не определены однозначно, пользователь выбирает вручную:

- проект;
- позицию потребности;
- количество;
- единицу измерения.

После подтверждения предложение попадает в соответствующую тендерную группу.

## 9.6. Выбор предложения

Полученный счёт является предложением и сам по себе не закрывает потребность.

Только действие `Выбрать предложение`:

- фиксирует поставщика;
- фиксирует выбранное количество;
- связывает строку счёта с потребностью;
- уменьшает остаток;
- обновляет `НЕ ЗАКАЗАНО`;
- обновляет индикаторы.

Разрешить:

- разных поставщиков для разных ТМЦ;
- разделение одной позиции между несколькими поставщиками;
- выбор части предложенного количества;
- отмену выбора;
- замену поставщика.

После отмены выбранное количество возвращается в `НЕ ЗАКАЗАНО`.

## 9.7. Сравнение предложений

Если есть несколько предложений, отображать их рядом.

Сравнивать:

- цену за единицу;
- общую сумму;
- количество;
- срок поставки;
- условия оплаты.

Минимальную цену и лучший срок можно выделять цветом. Автоматически выбирать поставщика запрещено.

Нельзя удалять или скрывать раздел №1. Все восемь разделов должны присутствовать всегда.

## 10.2. Итоговые строки разделов

Итоговая строка находится сверху каждого раздела.

В колонке `Реквизиты счёта / Наименование ТМЦ` отображается `ИТОГО:`.

Итоги:

- сумма заказа;
- оплачено;
- сумма к оплате.

Стрелка в строке раздела раскрывает и сворачивает счета. Кнопка `Отобразить все счета` раскрывает все разделы и снимает временные фильтры.

## 10.3. Колонки

1. № п/п;
2. Наименование поставщика;
3. Наименование плательщика;
4. Сальдо на дату;
5. СРОЧНО;
6. ПРИОРИТЕТ;
7. № заказа / Наименование проекта;
8. Реквизиты счёта / Наименование ТМЦ;
9. Сумма заказа;
10. Оплачено;
11. Сумма к оплате;
12. Дата прихода.

Если в утверждённой текущей версии присутствует `% в запуск`, сохранить его как отдельную колонку перед суммами. Нельзя удалять действующую колонку из-за расхождения старого прототипа и нового макета.

## 10.4. Просмотр счёта

Клик по ячейке `Реквизиты счёта / Наименование ТМЦ` открывает исходный счёт в модальном окне.

Поддержать:

- PDF и изображения внутри панели;
- Excel и TIFF — скачивание или открытие системным приложением;
- кнопку открытия в новой вкладке;
- сообщение, если файл перемещён или недоступен.

## 10.5. Верхняя область

Показывать:

- заголовок `ПЛАН ОПЛАТ`;
- текущую календарную дату формирования;
- фактическое количество счетов;
- общую сумму документов;
- общий итог;
- карточки приоритетов;
- семь карточек плательщиков;
- кнопку `ОБНОВИТЬ ДАННЫЕ`.

Дата и количество документов рассчитываются при открытии отчёта и после каждого обновления.

## 10.6. Приоритеты

- приоритет 1 — оплата на текущую дату, сверхсрочно;
- приоритет 2 — оплата в течение пяти рабочих дней;
- приоритет 3 — оплата в течение тридцати рабочих дней.

Приоритет определяется автоматически по срокам из заказа, но разрешено ручное изменение и удаление значения.

Ручное значение имеет приоритет над автоматическим до его отмены.

Карточки показывают `Сумма к оплате` по каждому приоритету.

## 10.7. Срочный план

В колонке `СРОЧНО` находятся чекбоксы.

Кнопка `СФОРМИРОВАТЬ`:

- оставляет на экране отмеченные строки;
- пересчитывает итоги;
- не удаляет остальные строки из базы;
- позволяет вернуться к полному списку.

## 10.8. Процент в запуск

Допустимые значения: 1–100% и пустое значение.

Показывать знак `%`.

Базовая формула:

```text
Сумма к оплате =
Сумма заказа − Оплачено − ранее учтённая часть согласно условиям запуска
```

Точное применение процента должно следовать условиям заказа и не допускать двойного вычитания одной оплаты.

## 10.9. Оплачено и полное погашение

Поле `Оплачено` допускает ручную корректировку пользователем с соответствующим правом.

Если оплачено не меньше полной суммы обязательства:

- строка исчезает из активного плана;
- счёт получает статус `Оплачен полностью`;
- остаётся в истории;
- повторный импорт не возвращает его в активный план;
- отмена полного погашения возможна только отдельным действием с записью в журнале.

## 10.10. Импорт оплат

Источник — файлы Excel/CSV из папки `imports\payments` или ручная загрузка.

Учитывать только строки, где `Вид операции = Оплата поставщику`.

Сопоставление:

- поставщик — строго из колонки `Контрагент` / `Поставщик` / `Получатель`;
- плательщик — из отдельной колонки плательщика / организации;
- назначение платежа используется для номера счёта, но никогда не заменяет поставщика;
- сумма — из колонки суммы операции.

Новые файлы оплат суммируются с ранее загруженными. Каждая операция имеет уникальный ключ и не учитывается повторно.

## 10.11. Сальдо БК-АЛПРОФ

Правило применяется только для поставщика `БК-АЛПРОФ`.

- дебет — раздел 1, красным цветом и со знаком минус;
- кредит — раздел 3, чёрным цветом;
- значение отображается один раз для каждого плательщика в первой подходящей строке;
- источник — файл сальдо;
- повторный импорт обновляет значение, а не дублирует его.

## 10.12. Фильтры плана оплат

Фильтры `ПОДБОР`:

- поставщик;
- плательщик;
- приоритет;
- № заказа / проект.

Фильтры влияют на строки, карточки приоритетов, карточки плательщиков и общие итоги.

# 18. Обязательные сценарии приёмки

## 18.1. Общие справочники

1. Все 65 поставщиков перенесены без потери и дублей.
2. Список поставщиков сортируется по алфавиту и показывается в четырёх столбцах.
3. У поставщика показываются ИНН, цвет ЗСК, источник и дата проверки.
4. При недоступном источнике старый результат не удаляется.
5. Неоднозначный ИНН не подтверждается автоматически.
6. Все категории ТМЦ присутствуют, отдельного окна `ЛИСТЫ оцинковка` нет.

## 18.2. Проекты и потребность

7. Проекты загружаются из колонки `Название проекта`.
8. Повторные названия в фильтре отсутствуют.
9. Выбор проекта загружает только его потребность.
10. Выбор нескольких проектов объединяет потребность и сохраняет принадлежность каждой строки.
11. Ошибочный новый файл не удаляет предыдущую успешную версию.

## 18.3. Счета и построчное сопоставление

12. Счёт с несколькими ТМЦ создаёт несколько строк.
13. Для каждой строки сохраняются наименование, единица, количество, цена и сумма.
14. Назначение платежа не попадает в поле поставщика.
15. Разные единицы измерения требуют ручного подтверждения.
16. Нечёткое совпадение является подсказкой и не закрывает потребность.
17. Повторный импорт того же файла не создаёт дубль.
18. Изменённый файл создаёт новую версию обработки без потери подтверждений.

## 18.4. Не заказано и тендер

19. В проекте есть потребность, счетов нет — все позиции находятся в `НЕ ЗАКАЗАНО`.
20. К проекту привязан счёт только на часть ТМЦ — остальные остаются необработанными.
21. Количество в выбранном счёте меньше потребности — `Заказано частично`.
22. Несколько счетов поставщиков на одну позицию показываются рядом.
23. До выбора предложения потребность не считается закрытой.
24. После выбора предложения остаток пересчитывается.
25. Несопоставленные строки попадают в `ТРЕБУЕТ ПРИВЯЗКИ`.
26. Отмена выбранного предложения возвращает количество в `НЕ ЗАКАЗАНО`.
27. Один счёт с несколькими ТМЦ связывается с несколькими позициями.
28. Одну позицию можно разделить между несколькими поставщиками.
29. Нельзя выбрать количество больше предложенного.
30. Сумма выбранных количеств может превышать потребность только после отдельного подтверждения предупреждения.

## 18.5. План оплат

31. На экране присутствуют все восемь разделов.
32. Строка заголовков расположена непосредственно над первым разделом.
33. Итоговые строки находятся сверху разделов.
34. Раскрытие раздела не нарушает расположение других разделов.
35. `Отобразить все счета` раскрывает все восемь разделов.
36. Фильтры пересчитывают строки и итоговые карточки.
37. Клик по реквизитам открывает правильный исходный счёт.
38. `СФОРМИРОВАТЬ` показывает только отмеченные срочные строки.
39. Ручной приоритет сохраняется после обновления.
40. Полностью оплаченный счёт исчезает и не возвращается при повторном импорте.
41. Повторный файл оплат не удваивает оплату.
42. Сальдо БК-АЛПРОФ отображается по утверждённым правилам.

## 18.6. Сохранность

43. После закрытия браузера данные сохраняются.
44. После перезапуска Docker данные сохраняются.
45. После перезагрузки Windows приложение запускается и показывает прежние данные.
46. Резервная копия восстанавливает базу и ссылки на документы.
47. Все ручные изменения присутствуют в журнале действий.
